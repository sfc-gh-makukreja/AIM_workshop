**Corrections forced by the dry-run:**

1. **Object count was wrong.** 11 tables, not 12 (10 in `tastybytes` +
   `etl_results.etl_logs`). Total is 18 objects: 1 db + 3 schemas + 11 tables +
   1 view + 1 function + 1 procedure. Fixed in README, labs 00/02/06.
2. **`setup.sql` must not drop `PUBLIC`.** The original draft did. The ETL deploy
   stages `etl_configuration` and file formats in `<db>.PUBLIC` and fails with
   `Schema 'TASTYBYTESDB.PUBLIC' does not exist or not authorized` (14 artifacts
   failed). Removed the `DROP SCHEMA`.
3. **Lab 07 was rewritten around the native path.** The ETL deploy produces a
   Snowflake `DBT PROJECT` object plus a task graph that mirrors the SSIS control
   flow (root → start log → `EXECUTE DBT PROJECT` → end log). Local `dbt build`
   is now optional (Lab 07.6), and dbt-core is no longer a prerequisite.
4. **Registered layout differs from the draft.** Databases and schemas land at
   `source/<db>/<db>.sql` and `source/<db>/<schema>/<schema>.sql`, one level
   above the typed folders. Lab 02 corrected.

**Gotchas now documented in the labs:**

- The dbt deploy needs a **current schema**. `--schema` on `scai code deploy` does
  not propagate to it; `SNOWFLAKE_DATABASE` / `SNOWFLAKE_SCHEMA` env vars (or
  connection defaults) do.
- There are **two copies** of the dbt project. `artifacts/_etl/...` is the
  conversion record; `snowflake/_etl/...` is what deploys. Editing only
  `artifacts/` has no effect — this cost a full debug cycle.
- The deploy resolves `sources.yml` `YOUR_SCHEMA` to the connection schema
  (`PUBLIC`), not to where the tables actually are (`TASTYBYTES`). Attendees must
  fix it; that is the stabilization lesson.
- Converted tasks carry `WAREHOUSE=DUMMY_WAREHOUSE`; deploy substitutes from the
  connection (`COMPUTE_WH`).
- Both log tasks insert the same `'...aggregate start'` message — a faithful
  conversion of a bug in the original package. Good teaching moment (Lab 07.5).

**Not verified:** the local `dbt build` loop in Lab 07.6 — `dbt` is not installed
on the build machine. The native path supersedes it, and it is marked optional.
Verify before relying on it in a session.

## Findings and decisions

- **Extracted source, not raw DDL.** The reference repo's older `migration/`
  project imported the multi-object `00_ddl.sql` and produced
  `source/tastybytesdb/dbo/unknown_type/00_ddl.sql` plus a spurious
  `source/master/` tree. The extracted per-object layout avoids both. If you
  ever see `unknown_type/` in an attendee project, the wrong input path was used.
- **No compute pool in `setup.sql`.** `TASTYBYTES_MIG_POOL` in the reference
  `init.sql` exists only for the data-migration worker (SPCS), which this
  workshop skips. Trial accounts may not have container services enabled.
- **ETL is a second `code add`.** `etl/` sits outside `source_db/`, so it needs
  its own `scai code add -i .../etl` **without** `--overwrite` — `--overwrite`
  would wipe the already-imported SQL in `source/`.
- **No `query_log.csv`.** Only needed for `test_seed_source: logs`, and testing
  is out of scope.

## What failed — do not retry

Record dead ends here so they are not repeated on the next revision.

- **Do not `DROP SCHEMA PUBLIC` in `setup.sql`.** Breaks the ETL deploy. See
  dry-run correction 2.
- **Do not fix dbt placeholders in `artifacts/_etl/`.** No effect on deploy. Edit
  `snowflake/_etl/` instead.
- **`scai code deploy --schema X` does not fix the dbt sub-deploy.** Tried; still
  failed with "does not have a current schema". Use env vars or connection
  defaults.
- **`configure(tasks={"createTests": false})`** is rejected — router node.
  **`captureBaseline`** is rejected — locked. Do not put either in the overlay.
- `ls migration/` immediately after a broad `find` in the reference repo
  returned "No such file or directory" once, then worked on retry. Transient FS
  caching, not a real absence. Not worth chasing.
- Multi-line heredocs (`python3 - <<'EOF'`) confused the persistent shell mid-run
  and left it hung. The script did execute, which made it look like a no-op. Use
  a temp script file or the editor tools instead.
